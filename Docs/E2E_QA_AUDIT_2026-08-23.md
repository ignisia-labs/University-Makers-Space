# MakerSpace End-to-End QA Audit

**Date:** 2026-08-23

**Frontend:** `http://127.0.0.1:5174`

**Backend:** `http://127.0.0.1:4000` (through the Vite `/api` and `/health` proxy)

**Browser:** Codex in-app Chromium browser, desktop and default responsive viewports

## Executive result

The frontend and backend are **not integrated end to end in the current working tree**. The visible frontend flows operate against `MakerSpaceProvider` browser-local state. Authentication, onboarding, project creation, logout, role selection, privileged user search, and audit views produced no `/api` requests.

The backend itself is reachable through the frontend proxy: `/health` returned 200, `/api/v1/auth/google/config` returned 200, and an unauthenticated protected reference-data request correctly returned 401. The frontend did not invoke those endpoints during normal UI flows.

No real MIT-WPU test-user credentials were present in the request or repository, so a real Google Workspace login and persisted role-account verification could not be executed. Generated QA identities were used only to exercise the current local prototype UI.

## Issues log

### QA-001 — Critical — Frontend does not call the backend

**Evidence:** Network capture across sign-in, onboarding, refresh, project submission, logout, Admin, Super Admin user search, and audit navigation contained zero `/api` requests.

**Impact:** UI success states do not prove persistence, authentication, authorization, transaction behavior, or multi-client consistency. The application cannot satisfy the Phase 1 integration gate.

**Expected:** Normal UI flows should use the shared API client and backend contracts.

### QA-002 — Critical — Non-institutional email is accepted by the frontend sign-in flow

**Steps:** Landing → Sign In → enter `qa.external@example.com` → Continue.

**Actual:** The UI accepted the email and navigated to `/onboarding`.

**Expected:** Authentication must occur through Google Identity Services, with the backend rejecting accounts outside the configured MIT-WPU Workspace domain.

### QA-003 — High — Sign-in identity is not carried into onboarding and email is editable

**Actual:** After entering an institutional-format email during sign-in, the onboarding email field was empty. Browser inspection showed it was neither read-only nor disabled.

**Expected:** Email should come from the verified Google identity and be read-only.

### QA-004 — High — Onboarding uses hardcoded reference data

**Evidence:** Department, programme, and academic-year selection produced no API traffic. Choosing Computer Science & Engineering still exposed generic programme options such as B.Des, MBA Tech, and Ph.D rather than department-filtered database records.

**Expected:** Load authenticated departments and years from the backend, then query programmes by selected department ID.

### QA-005 — Critical — UI authorization is prototype-state based

**Actual:** Landing-page Staff Access buttons opened Faculty/Lab Assistant/Admin workspaces directly in development. The Super Admin workspace was opened through the prototype role selector without an authenticated backend account. No `/auth/me` or permission request occurred.

**Impact:** Backend authorization cannot be tested from the UI, and privileged screens are populated independently of persisted roles.

**Expected:** Workspace access should derive from the authenticated backend user and returned permissions. Prototype switching must remain visually and behaviorally isolated from production authorization.

### QA-006 — High — Project submission is browser-local

**Actual:** Project creation, mentor selection, submission, toast, list update, cross-workspace counts, and audit entry all succeeded with zero project API calls.

**Impact:** No project, membership, mentor request, notification, audit, idempotency, or transaction behavior is exercised.

### QA-007 — High — Admin and Super Admin data are browser-local

**Actual:** User directory search, role/status filters, platform counts, equipment summaries, and audit records changed based on local prototype state without calling user, configuration, equipment, or audit APIs.

**Impact:** Privileged access management and audit integrity are not verified.

### QA-008 — Medium — Development API errors expose server stack traces and local paths

**Actual:** The expected 401 response from `/api/v1/reference-data/departments` included an Express stack trace and absolute local filesystem paths.

**Expected:** Client-facing error envelopes should omit internal stack traces even in a shared QA environment; detailed traces should remain in server logs.

### QA-009 — Medium — Super Admin shell renders an empty identity

**Actual:** The desktop Super Admin sidebar showed a blank name/avatar area and a bare `PRN` label.

**Expected:** Render the real authenticated privileged identity and omit Student-only PRN presentation where it does not apply.

### QA-010 — Medium — Frontend quality gate currently fails

**Actual:** The frontend production build passes, but lint reports 21 formatting errors and 7 Fast Refresh warnings. Backend lint/build, 15 tests, Prisma validation, and migration status pass.

## HTTP and console observations

- UI-driven API calls: none.
- UI-driven 4xx/5xx responses: none, because the frontend did not call the backend.
- Manual browser-origin smoke responses:
  - `GET /health`: 200.
  - `GET /api/v1/auth/google/config`: 200.
  - `GET /api/v1/reference-data/departments` without access token: expected 401.
- Console errors/warnings during tested UI flows: none captured.
- UI rendering defect confirmed: missing privileged identity in the Super Admin shell.

## Required retest sequence

1. Replace mock sign-in with Google Identity Services and the existing auth endpoints.
2. Keep the access token in memory and restore sessions through refresh plus `/auth/me`.
3. Connect onboarding and reference data.
4. Replace local project, Admin, and Super Admin state with the existing API clients.
5. Provide one Student MIT-WPU test account and one pre-provisioned Admin/Super Admin MIT-WPU test account.
6. Rerun the browser suite while asserting each request, response status, persisted database result, authorization boundary, refresh behavior, logout revocation, and cross-role UI update.
